# Feature Specification: 桌面高密度任务工作台与全局壳层重构

**Workspace**: `desktop-task-workspace-shell`  
**Created**: 2026-05-12  
**Status**: Draft  
**Input**: 用户描述: "现在开始对整体的 layout 进行优化，最大的问题是不重要的内容占据了大量空间；整体布局都要改，品牌化信息其实不需要，右侧详情只有选中任务时才展开，任务列表要更像 Things/滴答的紧凑行，使用 SDD 流程来做，桌面优先，先不考虑移动端和平板。"

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在桌面端获得高密度且聚焦任务的全局壳层 (Priority: P1)

作为日常在桌面端高频使用 Stride OS 的用户，我希望整个 dashboard 区域去掉无效留白和低频展示信息，让主操作区尽可能贴近视口边界，以便把空间优先让给真正需要操作的数据与列表。

**Why this priority**: 如果全局壳层不先收紧，任务页即使重构也会继续被外层边距、品牌块和账户卡片挤压，无法达到目标效率。

**Acceptance Scenarios**:

1. **[US1-1]**
   **Given** 用户进入任一 dashboard 内页面  
   **When** 页面渲染完成  
   **Then** 用户应看到更贴边、更像桌面应用窗口的主工作区，而不是被明显外层 padding 和壳层装饰包裹的内容区

2. **[US1-2]**
   **Given** 用户在 dashboard 内任一页面工作  
   **When** 用户观察左侧全局导航  
   **Then** 导航应以高密度工具栏形态存在，只保留核心模块入口和必要状态，不再占据大面积品牌文案、说明文案、账户卡片和重复退出入口

**Edge Cases**:

- **[US1-3]** 在导航收起为窄栏后，当前激活模块仍需可识别
- **[US1-4]** 在页面内容较少时，壳层仍需稳定，不得因移除品牌卡片而显得残缺
- **[US1-5]** 本次仅要求桌面端体验成立，不要求为移动端和平板提供等价布局

### User Story 2 - 在任务页优先获得最大操作空间 (Priority: P1)

作为需要持续扫读和处理任务的用户，我希望任务页默认把尽可能多的宽度给任务来源和任务列表，而不是长期被详情区和低频介绍信息切碎，以便更高效地浏览与完成任务。

**Why this priority**: 这是本轮优化的核心价值，直接决定任务页是否从“页面展示”转为“操作台”。

**Acceptance Scenarios**:

1. **[US2-1]**
   **Given** 用户进入任务页且当前没有选中任务  
   **When** 页面渲染完成  
   **Then** 页面应默认只显示来源栏和主列表两大工作区，不应预留常驻详情栏宽度

2. **[US2-2]**
   **Given** 用户在任务页浏览任务  
   **When** 用户未主动查看某个任务详情  
   **Then** 任务主列表应获得页面中的最大横向空间，并成为默认视觉焦点

**Edge Cases**:

- **[US2-3]** 当当前来源没有任何任务时，来源栏和主列表骨架仍需保留，不能退化成空白页
- **[US2-4]** 当任务很多时，主列表应可独立滚动，不受其他栏位影响
- **[US2-5]** 移除介绍性首屏模块后，关键操作入口仍需可见且可达

### User Story 3 - 仅在需要时展开任务详情 (Priority: P1)

作为浏览任务列表的用户，我希望任务详情只在真正选中任务后才展开，以便平时不浪费空间，只有需要查看上下文时才付出宽度成本。

**Why this priority**: 用户已经明确否定了常驻三栏；详情区必须从“默认占位”改为“按需上下文面板”。

**Acceptance Scenarios**:

1. **[US3-1]**
   **Given** 用户在任务主列表中点击某个任务行  
   **When** 任务进入选中状态  
   **Then** 右侧详情面板必须展开，并展示该任务的核心信息

2. **[US3-2]**
   **Given** 当前已有任务详情展开  
   **When** 用户取消选中、切换到不包含该任务的来源，或关闭详情面板  
   **Then** 详情面板必须收起，主列表宽度应立即回流扩大

**Edge Cases**:

- **[US3-3]** 当任务没有描述时，详情面板仍需保持稳定布局和空文案
- **[US3-4]** 当用户连续切换不同任务时，详情面板内容应稳定同步，不应闪烁或残留旧信息
- **[US3-5]** 详情展开后，来源栏与主列表的滚动定位不应被重置

### User Story 4 - 以更紧凑的行式列表处理任务 (Priority: P1)

作为偏好 Things / 滴答这类高密度任务工具的用户，我希望任务列表更像紧凑的行而不是大卡片堆叠，以便一屏看到更多任务、更快扫读标题和日期，并降低视觉噪声。

**Why this priority**: 仅仅调整栏位还不够；如果任务项继续保持高卡片密度，主列表仍会显得臃肿。

**Acceptance Scenarios**:

1. **[US4-1]**
   **Given** 用户查看任务主列表  
   **When** 任务行渲染完成  
   **Then** 每个任务项应以紧凑行式结构展示，至少包含完成状态、标题、必要标签和日期，整体高度明显低于当前卡片式实现

2. **[US4-2]**
   **Given** 用户在任务主列表中快速浏览多个分组  
   **When** 视觉扫描发生  
   **Then** 用户应能快速区分分组标题、选中态、完成态和普通任务，而不需要在大面积卡片边框与留白之间跳跃

**Edge Cases**:

- **[US4-3]** 已完成任务必须弱化但仍可读，不得因为压缩密度而失去状态可辨识性
- **[US4-4]** 在智能来源视图中，任务所属清单标识仍需可见
- **[US4-5]** 紧凑化不能以牺牲点击目标可用性为代价，checkbox 与任务行点击区域仍需稳定可操作

### User Story 5 - 用统一的桌面工作台逻辑承接后续页面 (Priority: P2)

作为持续迭代 Stride OS 的开发者，我希望这次壳层重构不仅服务任务页，还能为其他 dashboard 页面提供更高密度的统一框架，以便后续页面不再重复引入低效的大标题、说明文案和厚重卡片结构。

**Why this priority**: 本次虽然由任务页驱动，但改的是全局 shell；如果不把它定义成可复用骨架，后续页面仍会回到旧问题。

**Acceptance Scenarios**:

1. **[US5-1]**
   **Given** 用户进入 dashboard 内其他页面  
   **When** 页面渲染完成  
   **Then** 这些页面也应运行在同一套更贴边、更高密度的全局壳层之上，而不是仅任务页特殊处理

2. **[US5-2]**
   **Given** 后续继续迭代 OKR、四象限、复盘、设置页  
   **When** 复用新的页面骨架  
   **Then** 开发者应能沿用“紧凑导航 + 主工作区优先”的结构原则，而不是回到旧的品牌化 dashboard 模板

**Edge Cases**:

- **[US5-3]** 不同页面可以保留自己的主区结构，但不得重新引入大块无效首屏介绍
- **[US5-4]** 共用壳层调整不得破坏现有登录校验、主区滚动和导航高亮

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须将 dashboard 全局壳层改为桌面优先的高密度布局，显著减少当前外层 padding、壳层包裹感和无效留白。
- **FR-002**: 左侧全局导航必须保留核心模块入口，但移除大面积品牌文案、说明文案、用户卡片和重复退出入口等非核心展示内容。
- **FR-003**: 全局导航必须支持展开与收起两种桌面状态，展开时显示图标与文字，收起时显示高密度图标栏。
- **FR-004**: 导航收展状态应优先持久化到本地存储；若持久化不可用，切换能力本身仍必须可用。
- **FR-005**: dashboard 主内容区必须继续保持独立滚动，不得因壳层重构破坏现有滚动隔离。
- **FR-006**: 任务页必须移除当前 `PageIntro` 这类介绍式首屏模块，改为更轻量的工作台工具条。
- **FR-007**: 任务页默认布局必须优先展示来源栏和主列表；在未选中任务时，详情区不得常驻占位。
- **FR-008**: 任务页在选中任务后必须展开右侧详情面板，并在取消选中或上下文失效时收起该面板。
- **FR-009**: 详情面板展开与收起时，主列表宽度必须同步回流，不得保留无效空白列。
- **FR-010**: 任务页来源栏必须继续承载智能来源和真实清单两类来源切换能力，不得因密度优化丢失现有来源模型。
- **FR-011**: 任务主列表必须成为任务页默认视觉焦点和最大横向区域。
- **FR-012**: 任务主列表顶部必须保留核心工具条能力，至少包括当前来源标题、新建任务入口以及必要的排序/更多操作入口。
- **FR-013**: 任务项必须从大卡片结构收紧为更接近 Things / 滴答风格的紧凑行式结构。
- **FR-014**: 每个任务行必须至少展示 checkbox、标题、必要标签、截止日期，以及在智能来源视图下的清单来源标识。
- **FR-015**: 已完成任务必须有明确但克制的弱化视觉状态，支持在紧凑列表中快速区分。
- **FR-016**: 点击 checkbox 与点击任务行主体必须继续保留不同语义：前者切换完成状态，后者驱动选中和详情联动。
- **FR-017**: 任务页各工作区必须保持清晰分隔，至少包括来源栏、主列表和条件详情面板三种角色。
- **FR-018**: 主列表和详情面板必须支持各自独立滚动，避免一个区域内容过长时拖动整个页面结构。
- **FR-019**: 本次改造必须在桌面端优先成立，不要求同时覆盖移动端和平板端的等价体验。
- **FR-020**: 新的高密度全局壳层必须可被其他 dashboard 页面复用，不能把关键结构仅写死在任务页。

### Non-Functional Requirements *(if applicable)*

- **NFR-001**: 本次改造必须优先优化桌面端操作效率，而不是展示型视觉包装。
- **NFR-002**: 高密度化不能以牺牲基础可读性、可点击性和状态可辨识性为代价。
- **NFR-003**: 现有任务数据模型、任务完成逻辑、来源切换逻辑和登录访问控制必须保持业务连续性，不在本次需求中重构语义。

### Key Entities *(if applicable)*

- **全局工作台壳层**: dashboard 内各页面共享的桌面应用式容器，负责导航、主内容承载、滚动隔离和空间分配。
- **全局导航**: 壳层左侧的高密度模块入口区域，支持展开和收起两种桌面状态。
- **任务来源栏**: 任务页中用于选择智能来源与真实清单的侧栏。
- **任务主列表**: 任务页中默认占据最大空间的执行区域，以紧凑任务行承载浏览、勾选和选中。
- **条件详情面板**: 仅在存在选中任务时展开的右侧上下文区域，用于展示标题、描述和相关操作。

## Out of Scope *(if applicable)*

明确不在本次功能范围内的内容：

- 移动端和平板端的专门布局策略
- 任务模型迁移、历史数据兼容和导入导出
- 任务提醒、通知、协作、评论等新业务能力
- 排序、更多操作等入口背后的完整业务扩展
- 非任务页业务模块的深度信息架构重做
