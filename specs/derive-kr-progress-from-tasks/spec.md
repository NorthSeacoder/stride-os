# Feature Specification: KR Task Progress Summary And Check-in Reframe

**Workspace**: `derive-kr-progress-from-tasks`  
**Created**: 2026-05-14  
**Status**: Draft  
**Input**: 用户描述: "把 KR 进度改成任务驱动推导，check-in 用于覆盖修正。后续收敛为：KR 自动展示任务完成摘要，check-in 负责主观判断。"

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 自动从任务推导 KR 任务完成计数 (Priority: P1)

作为日常维护 OKR 的用户，我希望 KR 默认展示关联任务的完成计数视图，这样我不需要每次手工维护一个容易失真的百分比进度，也能让 KR 面板更贴近执行实际。

**Why this priority**: 这是本需求的核心价值。如果 KR 仍然完全依赖手工 check-in，本次需求就没有成立。

**Acceptance Scenarios**:

1. **[US1-1]**
   **Given** 一个 KR 关联了多条任务，且这些任务存在已完成与未完成状态  
   **When** 用户查看 OKR 列表页、KR 详情页或任何展示 KR 当前进度的页面  
   **Then** 系统默认展示该 KR 的任务完成计数视图，例如“已完成 X / 已承诺 Y”，而不是仅依赖最近一次 check-in

2. **[US1-2]**
   **Given** 一个任务已关联到某个 KR  
   **When** 该任务被标记完成、恢复未完成、取消与 KR 的关联，或新的“已承诺任务实例”被纳入该 KR  
   **Then** 该 KR 的任务完成计数会随之更新，并在后续读取中反映最新结果

3. **[US1-3]**
   **Given** 一个 KR 在推进中新增了关联任务  
   **When** 这些新任务只是执行过程中的补充拆解，而未明确纳入本期 KR 承诺范围  
   **Then** 它们不会自动进入 KR 的承诺任务总数，也不会影响该 KR 的默认任务完成计数视图

4. **[US1-4]**
   **Given** 一个 KR 没有关联任何任务  
   **When** 用户查看 KR 进度  
   **Then** 系统不会伪造百分比或推导值，而是展示“暂无承诺任务”之类的明确空状态

**Edge Cases**:

- **[US1-5]** 同一任务关联多个 KR 时，系统必须为每个 KR 独立参与推导，不能因为多重关联导致某个 KR 丢失进度来源。
- **[US1-6]** 已归档任务、已归档 KR、已归档 Objective / Period 的数据处理规则必须一致，不能把无效任务继续计入活跃 KR 的推导。
- **[US1-7]** 任务状态来回切换完成/恢复时，KR 推导进度必须可逆且幂等，不能累加出错误结果。
- **[US1-8]** 重复任务必须按“任务实例”参与统计；未生成的未来重复项不计入本期 KR 范围。

### User Story 2 - 用 check-in 补充主观进展判断 (Priority: P1)

作为 KR owner，我希望在自动任务计数之外，仍然可以通过 check-in 记录主观进展判断与信心，以表达“任务做完了但结果未达成”或“任务还没全做完但结果已接近达成”等现实情况。

**Why this priority**: 用户已明确要求保留 check-in 的修正能力。如果没有这层主观判断，系统只能看到任务执行量，看不到结果判断。

**Acceptance Scenarios**:

1. **[US2-1]**
   **Given** 一个 KR 已存在自动任务完成计数  
   **When** 用户提交新的 check-in，并填写手工进展判断  
   **Then** 系统保留自动任务完成计数作为客观执行视图，同时展示该次 check-in 作为主观进展判断

2. **[US2-2]**
   **Given** 一个 KR 已存在自动任务完成计数  
   **When** 用户提交新的 check-in，并仅更新总结/阻塞项/下一步/信心  
   **Then** 系统保留自动任务完成计数，同时应用最新 check-in 的附加说明与信心规则

3. **[US2-3]**
   **Given** 一个 KR 有历史 check-in 记录  
   **When** 用户查看 KR 详情页  
   **Then** 用户可以区分“自动任务完成计数”和“最近一次 check-in 判断”

**Edge Cases**:

- **[US2-4]** 新的任务完成变化发生在新的 check-in 之后时，系统仍然继续更新自动任务完成计数，但不会抹掉历史 check-in 记录。
- **[US2-5]** `confidence` 始终来自最近一次 check-in；当没有 check-in 时，系统明确返回“暂无信心记录”。

### User Story 3 - 保持复盘、风险识别与活动记录可解释 (Priority: P2)

作为使用 dashboard / review 的用户，我希望当 KR 进度来源变成“自动任务完成摘要 + check-in 主观判断”后，风险识别、复盘生成和活动轨迹仍然可解释，不会因为来源切换而让数据看起来前后矛盾。

**Why this priority**: 当前 dashboard 和 review 明显依赖 check-in 与 KR 当前值。如果这个变化不纳入验收，后续很容易出现“页面能看，但复盘和风险判断失真”的回归。

**Acceptance Scenarios**:

1. **[US3-1]**
   **Given** 一个 KR 没有新的 check-in，仅有自动任务完成计数  
   **When** 系统生成 dashboard 摘要或 review 草稿  
   **Then** 输出内容不会误报“没有进展”，并能使用新的自动任务完成计数与最近 check-in 信息

2. **[US3-2]**
   **Given** 一个 KR 存在手工 check-in 判断  
   **When** 用户查看活动轨迹或复盘上下文  
   **Then** 系统仍能保留 check-in 的时间线意义，而不是把它简化成普通任务变更

**Edge Cases**:

- **[US3-3]** 风险 KR 判定口径需要调整：缺少 check-in 仍然是风险信号，但必须结合任务完成摘要一起判断，而不是直接等同于风险。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须为每个 KR 计算一个“任务完成计数视图”，其输入至少包括当前周期内已纳入本期承诺范围的关联任务实例集合及这些任务的完成状态。
- **FR-002**: 系统必须将“KR 自动执行进展”定义为可解释的计数结果，至少包含 `已完成任务数`、`已承诺任务总数`、`未完成任务数`，而不是默认折算成百分比完成度。
- **FR-003**: 当 KR 存在承诺任务时，系统必须默认展示任务完成计数视图；当 KR 不存在承诺任务时，系统必须展示明确空状态。
- **FR-004**: 用户必须仍然能够通过 check-in 记录主观进展判断；该判断不需要与自动任务完成计数做数学合并。
- **FR-005**: 用户必须仍然能够通过 check-in 记录总结、阻塞项、下一步动作和信心，且这些字段的使用方式不能因为自动计数而丢失。
- **FR-005A**: `confidence` 不参与任务自动推导，始终由最近一次 check-in 维护。
- **FR-006**: 系统必须在任务创建、任务更新、任务完成、任务恢复、任务与 KR 关联变更后，保证后续读取到的 KR 进度与任务状态一致。
- **FR-006A**: 系统必须区分“任务关联到 KR”与“任务实例计入本期 KR 承诺进度”这两个概念；新增关联任务默认不进入承诺分母，只有显式纳入承诺范围后才参与推导。
- **FR-006B**: 系统必须将重复任务按实例处理；只有已经生成且已纳入本期承诺范围的任务实例才参与 KR 推导，未来未生成实例不参与。
- **FR-007**: KR 列表页、KR 详情页、Dashboard 摘要、Review 生成上下文以及对外 OKR API 在读取 KR 自动执行进展时，必须使用统一的计数规则。
- **FR-008**: KR 详情页必须让用户理解“自动任务完成计数”和“最近一次 check-in 判断”是两组并行信息，而不是混成单一当前值。
- **FR-009**: 系统必须保留 check-in 历史记录的时间线价值；手工覆盖不会抹掉历史 check-in，也不会抹掉任务变更活动。
- **FR-009**: 系统必须保留 check-in 历史记录的时间线价值；自动任务完成计数不会抹掉历史 check-in，也不会抹掉任务变更活动。
- **FR-010**: 当前已有数据必须兼容迁移：历史 KR、历史任务关联和历史 check-in 在升级后仍可被正确读取。
- **FR-011**: 当一个 KR 没有关联任务且也没有任何 check-in 时，系统必须返回明确的“暂无承诺任务 / 暂无信心记录 / 暂无 check-in 判断”结果，而不是伪造百分比或沿用过期值。
- **FR-012**: 系统第一版不要求把任务完成计数自动换算成 KR 百分比，也不要求把任务完成计数反推成 `numeric` KR 的真实业务数值。
- **FR-013**: 风险 KR 的判定口径必须调整：系统仍然需要把“没有 check-in”视为风险信号之一，但不能脱离任务完成摘要单独判定风险。

### Non-Functional Requirements *(if applicable)*

- **NFR-001**: 自动任务完成计数规则必须在服务层集中收敛，不能由不同页面各自拼装，以避免相同 KR 在不同界面出现不同结果。
- **NFR-002**: 新规则不能破坏现有活动记录、review 生成、dashboard 摘要与 API 路由的基本可用性。
- **NFR-003**: 对任务状态或任务-KR 关联的变更，KR 进度更新必须具备可重复计算能力，避免因事件顺序不同导致最终值不一致。

### Key Entities *(if applicable)*

- **Key Result**: OKR 中的关键结果，当前已有 `type`、`targetValue`、`currentValue`、`confidence`、`status` 等字段，也是现有 check-in 的记录对象。
- **Task**: 可被关联到一个或多个 KR 的执行项，当前至少包含完成状态、截止日期、优先级、归档状态，以及 `keyResultLinks` 关系。
- **KR Check-in**: KR 的人工更新记录，当前包含 `progressValue`、`confidence`、`summary`、`blockers`、`nextActions` 等字段。
- **KR Task Progress Snapshot**: 本需求引入的逻辑实体，表示系统按统一规则得到的“KR 自动执行进展视图”，其中需要包含已完成任务数、已承诺任务总数、未完成任务数、更新时间，以及与“承诺任务实例集合”相关的解释信息。

## Business Metrics *(optional — 上线后度量)*

- **BM-001**: 新建或维护 KR 时，用户为了表达“做了多少事”而频繁手工维护进度的次数下降，说明自动任务计数降低了维护成本。
- **BM-002**: Review / Dashboard 中因为“没有 check-in”而产生的伪风险数量下降，说明系统更贴近实际执行状态。

---

## Out of Scope *(if applicable)*

明确不在本次功能范围内的内容：

- 重做整套 OKR 数据模型或完全移除 check-in 能力
- 引入复杂的任务权重系统、任务工时估算体系或 AI 自动判断 KR 真实达成度
- 重新设计任务模块、Quadrant 模块或 Review UI 的整体交互结构
- 修改 OKR 的基础层级结构（Period / Objective / Key Result）

---

## Unclear Questions *(if applicable)*

- **UQ-004**: 风险 KR 的判定口径是否要调整？
  现有逻辑会把“没有 check-in”直接视作风险项。在自动任务计数上线后，这一规则需要重定义，但不再阻塞进入 plan；可在 plan 阶段具体化。
