## Background & Goals

当前任务页存在几类明显体验问题：

- 新建任务使用页面内插入表单，打断当前浏览上下文，且表单复杂度过高。
- 日期字段缺少合适的日期选择组件，当前录入方式不符合预期。
- 新建任务时存在 `Transaction function cannot return a promise` 报错，导致创建流程不稳定。
- 四象限页面通过点击按钮切换象限，交互不自然，与象限视图心智不匹配。
- dashboard 当前信息表达偏静态，缺少更直观的图表概览。
- 当前卡片圆角偏大，整体观感不够利落。
- 当前交互组件倾向原生封装，后续需要统一到 Base UI 组件底座，避免自建一套可访问性和键盘交互细节。

本次目标是把任务创建和四象限交互调整为更接近任务管理工具常见模式的体验，降低录入负担，修复创建失败问题，同时补强 dashboard 的信息表达，收紧卡片圆角风格，并统一使用 Base UI 作为交互组件底座，同时保持当前任务状态、KR 关联和今日/排期语义不变。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 以轻量方式创建任务 (Priority: P1)

作为日常管理任务的用户，我希望点击“新建任务”后进入一个覆盖式创建界面，而不是在当前页面直接插入大表单，以便更专注、更顺滑地快速录入任务。

**Why this priority**: 任务创建是高频入口，当前交互和报错同时影响可用性与转化。

**Acceptance Scenarios**:

1. **[US1-1]**
   **Given** 用户位于任务页任一视图  
   **When** 用户点击“新建任务”  
   **Then** 系统应打开 modal 创建容器，且不在页面内容区直接插入创建表单

2. **[US1-2]**
   **Given** 用户正在填写新任务  
   **When** 用户提交合法表单  
   **Then** 任务应创建成功、创建容器关闭、任务列表刷新，并在对应视图中可见

3. **[US1-3]**
   **Given** 用户打开新建任务界面  
   **When** 用户仅填写最小必填信息  
   **Then** 系统应允许完成快速创建，不要求用户先理解全部高级字段

**Edge Cases**:

- **[US1-4]** 用户取消创建时，系统应关闭创建容器且不污染页面布局
- **[US1-5]** 表单校验失败或服务端报错时，创建容器应保持打开，并清晰展示错误信息
- **[US1-6]** 已存在编辑任务流程时，新建与编辑不应互相干扰或同时展开多个冲突表单

### User Story 2 - 使用一致的日期选择交互 (Priority: P1)

作为创建或编辑任务的用户，我希望通过日期选择组件设置截止日期和排期日期，以便减少手输错误并获得一致交互。

**Why this priority**: 日期是任务管理的核心字段，当前缺少下拉/选择器是明显体验缺口。

**Acceptance Scenarios**:

1. **[US2-1]**
   **Given** 用户正在创建或编辑任务  
   **When** 用户操作截止日期或排期日期字段  
   **Then** 系统应提供统一的日期选择组件，而不是只依赖原始输入框

2. **[US2-2]**
   **Given** 用户将任务状态设为“已排期”  
   **When** 用户提交任务  
   **Then** 系统必须要求用户通过日期组件提供有效排期日期

**Edge Cases**:

- **[US2-3]** 用户清空日期时，系统应正确保存为空值，而不是残留旧日期
- **[US2-4]** 日期组件提交的值必须与现有服务端字段格式兼容

### User Story 3 - 稳定完成任务创建 (Priority: P1)

作为用户，我希望新建任务时不会因为事务错误失败，以便系统在录入高频场景下保持可靠。

**Why this priority**: 当前已出现创建时报错，属于直接阻断主流程的问题。

**Acceptance Scenarios**:

1. **[US3-1]**
   **Given** 用户提交一个合法的新任务  
   **When** 系统执行创建、KR 关联和审计写入  
   **Then** 整个流程不得触发 `Transaction function cannot return a promise` 报错

2. **[US3-2]**
   **Given** 用户创建任务并选择一个或多个 KR  
   **When** 创建成功  
   **Then** 任务本体、KR 关联和必要的后续刷新必须保持一致

**Edge Cases**:

- **[US3-3]** 未选择 KR 时，创建流程仍应成功
- **[US3-4]** 创建成功后重复刷新页面，不应出现部分写入或脏状态

### User Story 4 - 通过拖动管理四象限 (Priority: P2)

作为使用四象限视图管理优先级的用户，我希望直接把任务拖到目标象限，而不是点击一组动作按钮，以便更自然地完成任务归类。

**Why this priority**: 四象限的核心心智是“放置位置”，当前点击切换破坏了该模型。

**Acceptance Scenarios**:

1. **[US4-1]**
   **Given** 用户进入四象限页面  
   **When** 用户将任务拖到另一个象限  
   **Then** 系统应更新该任务的 `important` 与 `urgent` 值，并在新象限中显示

2. **[US4-2]**
   **Given** 用户完成一次拖动  
   **When** 页面刷新后  
   **Then** 任务应仍保留在新的象限位置

**Edge Cases**:

- **[US4-3]** 拖动失败或保存失败时，系统应给出可见反馈，且任务位置不能静默错乱
- **[US4-4]** 对不适合拖动的输入方式，系统仍需保留可访问的替代操作

### User Story 5 - Dashboard 信息表达更直观 (Priority: P3)

作为查看全局进展的用户，我希望 dashboard 增加合适的图表概览，并让卡片风格更克制一些，以便更快理解状态且界面更统一。

**Why this priority**: 这会影响首页观感和信息扫描效率，但不阻断任务主流程，因此优先级低于创建与四象限交互。

**Acceptance Scenarios**:

1. **[US5-1]**
   **Given** 用户进入 dashboard  
   **When** 页面加载完成  
   **Then** 系统应展示至少一组能反映任务/执行状态的图表化信息，而不只依赖纯文本或数字卡片

2. **[US5-2]**
   **Given** 用户浏览 dashboard 与相关卡片区域  
   **When** 对比现有样式  
   **Then** 卡片圆角应明显小于当前版本，整体观感更紧凑统一

**Edge Cases**:

- **[US5-3]** 当某些统计数据为空时，图表仍应有合理的空状态，而不是渲染异常
- **[US5-4]** 圆角调整不应破坏现有布局、点击热区或内容截断表现

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须将“新建任务”入口改为打开 modal 创建界面，而不是在任务页正文内直接插入表单。
- **FR-002**: 新建任务流程必须支持“快速创建优先，扩展字段按需填写”的交互结构，减少首次暴露的复杂度。
- **FR-003**: 系统必须在任务创建和任务编辑中为日期字段提供统一的日期选择组件。
- **FR-004**: 当任务状态为“已排期”时，系统必须确保排期日期可被选择、校验并正确提交。
- **FR-005**: 系统必须修复新建任务流程中的事务错误，确保合法任务创建不会触发 `Transaction function cannot return a promise`。
- **FR-006**: 修复后，任务创建与 KR 关联逻辑必须继续可用，不得破坏审计日志和页面刷新行为。
- **FR-007**: 系统必须把四象限任务移动的主交互改为拖动放置。
- **FR-008**: 四象限拖动完成后，系统必须仅更新任务的象限属性，不改变任务流程状态语义。
- **FR-009**: 系统必须在任务创建、日期选择、四象限拖动这三类核心流程中提供明确的成功/失败反馈。
- **FR-010**: 现有任务列表视图（今日、收件箱、已排期、已完成）的业务含义必须保持不变。
- **FR-011**: 系统必须在 dashboard 中增加合适的图表化展示，用于更直观呈现任务或执行状态。
- **FR-012**: 新增图表必须使用当前系统已有数据或本次范围内可直接聚合的数据，不引入新的长期运营数据依赖。
- **FR-013**: 系统必须缩小 dashboard 和相关任务卡片的圆角风格，使视觉更克制统一。
- **FR-014**: 新增或重构的 modal、popover、form field、select、toast 等交互组件必须优先基于 Base UI，不再新增纯原生封装作为长期组件底座。
- **FR-015**: 日期选择组件必须使用 Base UI 的弹层、字段和表单能力承载交互外壳，并使用 `react-day-picker` 提供日期选择核心，不得退回散落原生日期输入。

### Non-Functional Requirements *(if applicable)*

- **NFR-001**: 任务创建主流程必须稳定可用，不允许出现当前已知阻断性报错。
- **NFR-002**: 新交互必须兼容桌面端与移动端常见使用场景，不得只适配单一屏幕形态。
- **NFR-003**: 新建任务与四象限交互调整后，相关页面仍需满足现有应用的基础可访问性要求，包括表单可操作性和替代交互。
- **NFR-004**: dashboard 图表与样式调整不得明显拖慢首页首屏可用性。

### Key Entities *(if applicable)*

- **Task**: 任务实体，包含标题、备注、状态、今日类型、排期日期、截止日期、重要/紧急、优先级、精力等属性。
- **Task-KR Link**: 任务与 KR 的关联关系，需在创建和更新流程中保持一致性。
- **Quadrant Projection**: 由 `important` 与 `urgent` 两个布尔值投影出的四象限视图，不单独引入新的业务实体。

## Out of Scope *(if applicable)*

明确不在本次功能范围内的内容：

- 不重构任务状态模型本身（`inbox`、`today`、`scheduled`、`done`、`canceled` 的定义不变）
- 不改动 KR、Objective、Review 等其他模块的业务规则
- 不要求完整复刻滴答清单的全部视觉或高级交互，仅以其“轻量、快速、覆盖式创建”的体验作为参考
- 不在本次范围内新增任务提醒、重复任务、自然语言识别日期等扩展能力
- 不在本次范围内引入重型 BI、自定义报表系统或多维图表配置能力
- 不在本次范围内迁移全站所有历史 UI 组件；全站 Base UI 迁移后续单独开 feature 推进
