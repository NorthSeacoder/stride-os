# Feature Specification: 重塑 Dashboard 工作台视觉壳层

**Workspace**: `redesign-dashboard-shell`  
**Created**: 2026-05-10  
**Status**: Draft  
**Input**: 用户描述: "结合 sdd 流程来做吧"，以及后续补充“继续优化”要求：当前项目 `dashboard / okr / tasks / quadrants / review / settings` 六个页面需要继续统一视觉与壳层交互，方向为 `A 横向主骨架 + 铝金属工作台`，同时优化组件体系可维护性、设置页导航体验、主区域滚动行为，以及 Tailwind CSS 变量类名写法；其中组件治理的重点是使用 `shadcn` 作为组件管理层来组织基于 `Base UI` 的能力。

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 进入统一且高可用的工作台壳层 (Priority: P1)

作为日常使用 Stride OS 的用户，我希望进入任一 dashboard 页面时都处在同一套稳定、清晰、质感统一的工作台壳层中，以便快速建立空间感和操作预期。

**Why this priority**: 这是本次改造的基础。若壳层不统一，后续单页视觉升级会割裂，无法形成完整产品感。

**Acceptance Scenarios**:

1. **[US1-1]**
   **Given** 用户已登录并进入 `dashboard / okr / tasks / quadrants / review / settings` 任一页面  
   **When** 页面渲染完成  
   **Then** 用户应看到一致的左侧主导航与主内容工作区结构，页面级固定壳层信息不得重复挤占主要操作空间

2. **[US1-2]**
   **Given** 用户在上述页面间切换  
   **When** 页面跳转完成  
   **Then** 壳层结构、导航行为、主视觉语言必须保持一致，不得像进入不同产品

**Edge Cases**:

- **[US1-3]** 当页面内容较长时，主内容区域应独立滚动，不得连带侧边栏一起滚动而破坏定位感
- **[US1-4]** 当页面内容较短或为空时，壳层结构仍需稳定，不得塌陷或显得像临时占位页
- **[US1-5]** 在较窄桌面宽度或平板宽度下，导航和主内容仍需可用，不得遮挡主内容

### User Story 2 - 感知明确的“铝金属工作台”视觉语言 (Priority: P1)

作为关注产品观感的用户，我希望整个 dashboard 区域具有统一且明确的“铝金属工作台”质感，而不是普通深色 SaaS 后台，以便产品气质更高级、更有辨识度。

**Why this priority**: 用户已经明确给出审美方向；若视觉系统不落地，改造目标等于未完成。

**Acceptance Scenarios**:

1. **[US2-1]**
   **Given** 用户查看任一 dashboard 页面  
   **When** 对比改造前后  
   **Then** 页面应体现深石墨底、枪灰/铝金属面板、冷白细边、高度克制的冰蓝点缀，而非泛化深色卡片样式

2. **[US2-2]**
   **Given** 用户浏览卡片、导航、状态条、详情区等核心模块  
   **When** 视觉元素被观察  
   **Then** 这些区域应共享同一套边框、层次、圆角、阴影和高光规则

**Edge Cases**:

- **[US2-3]** 视觉强化不得依赖大面积霓虹、过度玻璃化或炫技动画
- **[US2-4]** 深色主题下仍需保证正文、次要信息和状态信息的可读性

### User Story 3 - 更高效地扫描核心页面信息 (Priority: P1)

作为每天高频使用目标、任务、四象限和复盘页面的用户，我希望每个页面在保持统一视觉的同时，具备清晰的布局骨架和主次焦点，以便我能快速完成扫描、判断和操作。

**Why this priority**: 这决定了视觉升级是否真的改善使用效率，而不是仅仅“变好看”。

**Acceptance Scenarios**:

1. **[US3-1]**
   **Given** 用户进入 `dashboard` 页面  
   **When** 页面加载完成  
   **Then** 用户应能快速区分总览区、核心进展区和摘要区，而不是面对一组无主次的卡片

2. **[US3-2]**
   **Given** 用户进入 `okr`、`tasks`、`quadrants`、`review`、`settings` 任一页面  
   **When** 页面内容可见  
   **Then** 每个页面都应存在明确的主区域与辅助区域，且布局与该页面任务相匹配

**Edge Cases**:

- **[US3-3]** 当数据量较少时，布局仍需成立，不能因空数据而失去结构重心
- **[US3-4]** 当数据量较多时，页面仍需维持清晰层级，不得因为视觉包装导致信息拥堵

### User Story 4 - 设置页导航与账户控制更符合系统心智 (Priority: P1)

作为需要偶尔查看账户信息、管理令牌和后续偏好的用户，我希望设置页二级导航和账户控制是稳定、可预期的，而不是出现重复信息、不可点击分组或跳转后仍像总览页一样混杂。

**Why this priority**: 设置页是当前壳层问题最集中的地方，若信息结构不清，整个系统控制台心智会被破坏。

**Acceptance Scenarios**:

1. **[US4-1]**
   **Given** 用户进入 `/settings` 或 `/settings/tokens`  
   **When** 页面渲染完成  
   **Then** 用户应能清楚区分“分组导航”与“当前分组内容”，且导航状态与当前路由一致

2. **[US4-2]**
   **Given** 用户需要查看当前登录身份或退出登录  
   **When** 用户观察壳层固定区域  
   **Then** 账户身份信息与退出操作应收敛到侧边栏或同一稳定控制区，不应与主内容顶部重复出现

**Edge Cases**:

- **[US4-3]** 当前尚未开放的偏好分组不得伪装成可用入口；若暂未实现，应明确表现为占位或未开放状态
- **[US4-4]** 在 `/settings/tokens` 等子页面中，设置导航仍需完整可见，不得丢失当前分组定位

### User Story 5 - 组件体系覆盖更完整的基础交互能力 (Priority: P2)

作为持续迭代该项目的开发者，我希望当前 UI 组件体系能覆盖常见控制台场景的标准能力，例如日期选择、图表展示和统一组件管理，并通过 `shadcn` 统一组织基于 `Base UI` 的组件能力，以便后续页面扩展时不再频繁自造轮子或留下分裂的交互风格。

**Why this priority**: 用户已明确关注组件体系的完整度与管理方式；如果这层目标不写入规格，后续实现可能只做页面表面修补。

**Acceptance Scenarios**:

1. **[US5-1]**
   **Given** 后续页面继续扩展统计、日期筛选或设置类交互  
   **When** 设计新界面  
   **Then** 应存在一套统一、可复用、可维护的组件基础能力来承接这些需求，且组件管理方式应保持集中、一致

2. **[US5-2]**
   **Given** 用户在不同页面看到日期输入、图表或其他标准控件  
   **When** 对比交互与样式  
   **Then** 它们应保持一致的语言和质量，而不是页面各自为政

**Edge Cases**:

- **[US5-3]** 新的组件体系目标不得要求一次性重写全部现有 UI；允许分阶段迁移，但不能继续扩大临时封装面积
- **[US5-4]** 组件能力增强不得破坏现有表单、导航和反馈组件的可用性

### User Story 6 - Dashboard 图表表达升级为可复用组件 (Priority: P2)

作为每天查看工作台总览的用户，我希望 dashboard 里的统计分布和负载信息能通过统一图表组件表达，而不是长期停留在临时条块或手工拼装状态，以便更快识别系统失衡点和执行压力。

**Why this priority**: 当前 dashboard 已经有聚合统计字段和基础图形表达，但图表层仍然偏临时；既然要收拢到 `shadcn` 组件体系，就应明确 dashboard 图表范围。

**Acceptance Scenarios**:

1. **[US6-1]**
   **Given** 用户进入 `dashboard` 页面  
   **When** 查看任务池、执行负载或风险摘要  
   **Then** 图表表达应来自统一、可复用的图表组件层，而不是页面私有手绘实现

2. **[US6-2]**
   **Given** 用户比较 dashboard 内不同统计模块  
   **When** 观察图表样式与交互  
   **Then** 图表容器、图例、色彩映射和空态表达应保持一致，不得每块统计各用一套语言

**Edge Cases**:

- **[US6-3]** 当统计值全为零或数据缺失时，图表区域仍需提供稳定空态，不能显示损坏或误导性图形
- **[US6-4]** 图表增强不得替代关键数字摘要；核心指标仍需可直接扫描

### User Story 7 - 四象限页面具备全站最高辨识度 (Priority: P2)

作为使用四象限进行优先级判断的用户，我希望四象限页面比其他页面更像一个“精密规划盘”，以便快速建立空间判断并感知它是系统中的核心差异化页面。

**Why this priority**: 四象限页是本次视觉语言最能拉开差异的一页，但不高于整体壳层统一性。

**Acceptance Scenarios**:

1. **[US7-1]**
   **Given** 用户进入 `quadrants` 页面  
   **When** 页面展示完成  
   **Then** 中央 2x2 象限区域必须成为视觉焦点，几何分区清楚，任务详情区为辅助焦点

2. **[US7-2]**
   **Given** 用户在六个页面之间比较  
   **When** 视觉特征被观察  
   **Then** `quadrants` 页应是“锋利感”和“精密感”最强的一页，但仍属于同一套产品系统

**Edge Cases**:

- **[US7-3]** 象限区域在数据较少时不能显得空洞无支撑
- **[US7-4]** 象限区域在数据较多时不能因为装饰性过强而弱化任务可读性

### User Story 8 - 低风险地完成视觉升级与样式治理 (Priority: P2)

作为维护该项目的开发者，我希望这次改造在不改变核心业务语义的前提下完成视觉重塑，以便降低回归风险并让后续实现可控。

**Why this priority**: 本次目标是界面系统升级，不是业务重构；边界必须清楚。

**Acceptance Scenarios**:

1. **[US8-1]**
   **Given** 用户使用现有导航和页面入口  
   **When** 视觉升级完成  
   **Then** 各页面业务功能、页面路由和核心信息语义必须保持连续，不要求用户重新学习产品结构

2. **[US8-2]**
   **Given** 用户在视觉升级后继续使用任务、OKR、复盘、设置等页面  
   **When** 核心信息呈现  
   **Then** 页面可新增或重排模块，但不得删除完成当前关键任务所必需的信息

**Edge Cases**:

- **[US8-3]** 视觉升级不应导致已有按钮、链接、表单入口因对比度或层级问题而难以发现
- **[US8-4]** 若某页本身结构较简单，也不能被强行塞入不必要的装饰模块
- **[US8-5]** 样式治理不应继续放大 Tailwind 警告和变量写法不一致问题

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须为 `dashboard / okr / tasks / quadrants / review / settings` 六个页面建立统一的 dashboard 壳层结构，至少包括左侧主导航和主内容工作区；固定壳层信息应服务导航与定位，不得重复占用主操作区。
- **FR-002**: 系统必须让六个页面共享同一套基础视觉变量和容器风格，包括背景层级、面板层级、边框规则、圆角规则、文字层级和状态强调方式。
- **FR-003**: 系统必须将本次视觉方向落实为“铝金属工作台”，具体表现为深石墨背景、枪灰/铝金属面板、冷白高光边和极少量冰蓝点缀，而不是普通深色后台模板。
- **FR-004**: 系统必须降低当前页面的“通用卡片堆叠感”，让每个页面具有清晰的主区域与辅助区域。
- **FR-005**: `dashboard` 页面必须重组为更明确的总览布局，至少能区分全局状态、核心进展和辅助摘要三类区域。
- **FR-006**: `okr` 页面必须突出“当前目标工作台”心智，明确区分目标列表区域和目标详情区域。
- **FR-007**: `tasks` 页面必须突出“执行控制台”心智，明确区分任务流区域和今日执行/辅助操作区域。
- **FR-008**: `quadrants` 页面必须突出中央 2x2 象限盘作为核心焦点，并保留配套的任务详情或辅助信息区域。
- **FR-009**: `review` 页面必须具备更安静、更偏分析和反思的布局气质，不得与执行型页面完全同质化。
- **FR-010**: `settings` 页面必须呈现为系统控制台式分组配置界面，而不是零散表单拼接。
- **FR-011**: 侧边栏中的账户身份信息、当前用户展示与退出登录入口必须整合到同一稳定控制区，避免与主内容顶部重复。
- **FR-012**: 主内容区域在长页面场景下必须支持独立滚动，侧边栏与壳层定位信息不得随主内容一起滚动失位。
- **FR-013**: `settings` 分组导航必须与当前子路由状态严格对应；未开放分组必须明确标识为占位或禁用，而不是表现为可点击但无结果。
- **FR-014**: `settings` 首页与子页面必须共享稳定的二级导航骨架，但每个页面主区域只展示当前分组相关内容，避免“首页信息在所有设置页都重复出现”的观感。
- **FR-015**: 系统必须为后续日期选择、图表展示和其他标准控制台控件保留统一、可复用的组件能力目标，避免继续扩大零散临时封装。
- **FR-016**: 共享组件层必须以 `shadcn` 作为主要管理与组织方式，用来承接基于 `Base UI` 的 primitives、样式封装与后续组件扩展。
- **FR-017**: 日期选择相关交互必须优先收敛到 `shadcn` 组件体系提供的 calendar/date-picker 方案，而不是继续扩大页面私有日期控件封装。
- **FR-018**: 表单能力必须纳入统一治理；对于需要更完整字段状态、校验与组合能力的客户端表单场景，应优先评估并采用 `@tanstack/react-form` 与 `shadcn` 表单模式的组合，而不是继续散落使用低一致性的自管理表单逻辑。
- **FR-019**: `dashboard` 页面必须梳理并收敛首批统一图表需求，至少覆盖“任务状态分布”“今日执行负载分布”与“风险/闭环摘要中的可视统计表达”三类场景。
- **FR-020**: 六个页面中的中文文案和主要功能入口必须继续可见、可识别，不得因纯视觉追求降低可用性。
- **FR-021**: 页面间导航必须继续支持用户快速在六个页面之间切换，且当前所在页面应有明确定位反馈。
- **FR-022**: 本次改造允许调整页面模块顺序、容器样式和信息编排，但不得改变现有页面的业务边界和路由职责。

### Non-Functional Requirements *(if applicable)*

- **NFR-001**: 本次视觉升级不得引入明显的首屏性能退化，避免依赖重型、连续性强的纯装饰效果。
- **NFR-002**: 深色视觉下必须保持足够的文字与交互控件可读性，避免高端感以牺牲可用性为代价。
- **NFR-003**: 页面布局必须兼容常见桌面宽度，并在较窄宽度下保持导航、状态栏与主内容基本可用。
- **NFR-004**: 本次 feature 必须保持与现有业务服务层和数据结构兼容，不以新增后端能力作为完成前提。
- **NFR-005**: 样式实现必须遵循当前 Tailwind CSS 的最佳实践，优先消除可自动规约的变量类名告警与重复写法，降低样式层维护噪音。
- **NFR-006**: 组件体系演进应优先考虑组件管理完整度、一致性与后续扩展成本，而不是只满足当前单页需求。
- **NFR-007**: 组件治理应尽量复用 `shadcn` 官方已有能力与推荐组合，减少项目长期维护自定义低层 primitive 的负担。

### Key Entities *(if applicable)*

- **Dashboard Shell**: 覆盖六个页面的统一工作台壳层，包括导航、状态栏、主画布和共享视觉规则。
- **Page Workspace**: 各页面在统一壳层内的专属主内容布局，如总览、目标工作台、执行控制台、象限盘、复盘台、设置控制台。
- **Visual Design Tokens**: 支撑本次视觉升级的颜色、边框、圆角、阴影、高光和层级规则。
- **Settings Control Index**: 设置页共享的分组导航与分组状态模型，用于稳定承载账户、令牌、偏好等控制项。
- **Shared UI Primitive Layer**: 支撑日期、图表、表单与反馈等标准交互的一致组件能力层。
- **Dashboard Chart Set**: dashboard 首批统一图表集合，至少包括任务状态分布、今日执行负载分布，以及用于风险或闭环摘要的辅助统计表达。

## Out of Scope *(if applicable)*

明确不在本次功能范围内的内容：

- 不新增新的业务模块、页面路由或产品流程
- 不修改任务、OKR、复盘、设置等模块的核心业务规则
- 不在本次范围内重构服务层、数据库结构或 API 语义
- 不要求在本次 spec 阶段直接决定具体采用哪一个第三方 UI 组件库或一次性完成全量迁移
- 不要求把整站所有非 dashboard 区域一并升级到同一视觉语言
- 不要求引入复杂动效、3D 场景或高度实验性的交互特效
- 不以“完全复刻 Apple 官方界面”为目标，只借用其克制、精密、材质化的设计原则
