# Feature Specification: 四象限任务视图重构

**Workspace**: `rebuild-task-quadrants`  
**Created**: 2026-05-12  
**Status**: Draft  
**Input**: 用户描述: "重构 `apps/web` 中的四象限页面，使其成为任务实体上的派生视图；四象限归属必须由 `priority + dueDate + today` 计算得到，不再使用与任务真相脱节的平行实体。页面采用 2×2 均分布局，支持按清单分组、显示已完成切换、每象限新建任务、整行拖拽跨象限/跨清单，并在跨日时自动按日期语义迁移。当前项目未投入使用，可直接删除旧 `important/urgent` 模型并清空旧任务数据。"

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 以四宫格浏览任务优先级 (Priority: P1)

作为需要快速判断任务先后顺序的用户，我希望四象限页将任务稳定地投影到 2×2 宫格中，以便在一个页面内直观看到重要性和紧急性的组合分布。

**Why this priority**: 这是页面存在的核心价值；若象限布局和归属规则不稳定，后续新建、拖拽和完成态交互都没有意义。

**Acceptance Scenarios**:

1. **[US1-1]**
   **Given** 用户进入 `/quadrants`  
   **When** 页面渲染完成  
   **Then** 主内容区必须显示 2 列 × 2 行且面积相等的四个象限块，顺序固定为左上 Q1、右上 Q2、右下 Q4、左下 Q3

2. **[US1-2]**
   **Given** 某个象限内存在未完成任务  
   **When** 页面渲染该象限  
   **Then** 任务必须按所属清单分组显示，组头展示清单图标、清单名称和任务数量

**Edge Cases**:

- **[US1-3]** 当某个象限没有任务时，该象限必须显示明确空态，而不是空白容器
- **[US1-4]** 当某个象限只有已完成任务且“显示已完成”关闭时，该象限仍需显示空态
- **[US1-5]** 四个象限的标题、边界和层次必须在桌面常见宽度下保持可辨识，不能因为内容为空而塌陷

### User Story 2 - 依据统一规则计算象限归属 (Priority: P1)

作为需要信任系统分类结果的用户，我希望任务总是根据优先级和截止日期被一致地映射到四象限，而不是依赖另一套独立字段，以便编辑任务后象限位置自然正确。

**Why this priority**: 用户已明确要求四象限是任务的派生视图，且禁止再造平行真相；这是本次重构的核心约束。

**Acceptance Scenarios**:

1. **[US2-1]**
   **Given** 任务有截止日期且其日历日差 `D <= 7`  
   **When** 系统计算四象限归属  
   **Then** 该任务必须被判定为“高紧急”

2. **[US2-2]**
   **Given** 一条任务为“今天 + 高优先级”  
   **When** 页面计算其象限  
   **Then** 结果必须为 Q1

3. **[US2-3]**
   **Given** 一条任务为“约 1 个月后 + 低优先级”  
   **When** 页面计算其象限  
   **Then** 结果必须为 Q4

**Edge Cases**:

- **[US2-4]** 无截止日期任务不得落入“无法分类”状态，而必须按优先级直接映射：`P1->Q1`、`P2->Q2`、`P3->Q3`、`null->Q4`
- **[US2-5]** 完成态任务仍需能被计算象限，但是否展示由“显示已完成”开关控制
- **[US2-6]** 跨日后若 `D` 变化导致紧急度分区变化，未完成任务必须在下次页面读取时自动归入新象限

### User Story 3 - 在象限内直接新建和编辑任务 (Priority: P1)

作为在优先级视图中规划任务的用户，我希望每个象限都能直接新建任务，并确保默认值使任务保存后落回当前象限，以便无需先去任务页再回来调整。

**Why this priority**: 页面不能只做查看；若新建入口与象限规则断裂，用户会马上遇到“刚创建就跑到别的象限”的反直觉行为。

**Acceptance Scenarios**:

1. **[US3-1]**
   **Given** 用户点击某个象限右上角的“新建任务”入口  
   **When** 新建弹窗打开  
   **Then** 表单中至少 `priority` 和 `dueDate` 的默认值必须保证任务保存后落在该象限

2. **[US3-2]**
   **Given** 用户点击象限内某条任务行的正文区域  
   **When** 编辑弹窗打开  
   **Then** 交互与任务页编辑体验保持一致，并允许编辑优先级和截止日期

**Edge Cases**:

- **[US3-3]** 若用户在弹窗内修改优先级或截止日期导致象限变化，保存后任务应出现在规则计算得到的新象限
- **[US3-4]** 若创建失败，弹窗不得静默关闭，且需保留当前输入
- **[US3-5]** 若象限默认反演值与用户手动修改冲突，最终以用户显式输入为准

### User Story 4 - 通过整行拖拽调整象限或清单归属 (Priority: P1)

作为需要快速重排任务的用户，我希望直接拖动整行任务来改变象限或清单归属，同时 checkbox 仍然可以单独点击，以便兼顾批量整理和快速完成。

**Why this priority**: 拖拽是四象限页的高频核心交互之一；如果不能准确回写底层字段，页面就会和任务真相脱节。

**Acceptance Scenarios**:

1. **[US4-1]**
   **Given** 用户将一条任务拖入另一个象限  
   **When** 放置完成  
   **Then** 系统必须按唯一反演表更新 `priority` 与 `dueDate`，并使规则计算结果等于目标象限

2. **[US4-2]**
   **Given** 用户将一条任务拖到同一象限下的另一清单分组  
   **When** 放置完成  
   **Then** 系统必须只更新 `listId`，且该任务的象限归属保持不变

3. **[US4-3]**
   **Given** 用户单击任务行左侧 checkbox  
   **When** 点击生效  
   **Then** 系统必须切换完成态，而不是开始拖拽

**Edge Cases**:

- **[US4-4]** 拖拽失败时，任务应回退到原始位置并给出错误反馈
- **[US4-5]** 同一象限同一清单内排序不在本次范围内，不要求持久化组内顺序
- **[US4-6]** 若目标清单分组为空，也必须允许作为放置目标

### User Story 5 - 控制是否显示已完成任务 (Priority: P2)

作为查看当前待办压力的用户，我希望按需显示或隐藏已完成任务，以便在复盘和专注两种模式之间切换。

**Why this priority**: 这是页面唯一的顶部全局选项，直接影响信息密度，但不改变底层任务数据。

**Acceptance Scenarios**:

1. **[US5-1]**
   **Given** 用户点击页面右上角 `...` 菜单中的“显示已完成”  
   **When** 开关状态变化  
   **Then** 四个象限中的已完成折叠区必须同步显示或隐藏

2. **[US5-2]**
   **Given** 某象限同时存在未完成和已完成任务  
   **When** “显示已完成”开启  
   **Then** 已完成任务必须在该象限内作为独立折叠区显示，而不是与未完成混排

**Edge Cases**:

- **[US5-3]** 切换“显示已完成”不得触发任务数据被误更新
- **[US5-4]** 某象限无已完成任务时，开启开关后也不应出现空的已完成区块

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须将 `/quadrants` 页面重构为任务实体上的派生视图，不得引入与全局任务脱节的平行四象限实体。
- **FR-002**: 页面顶部必须显示标题“「四象限」”。
- **FR-003**: 页面右上角必须提供 `...` 更多菜单，且菜单中首版只有“切换是否显示已完成”一个功能。
- **FR-004**: 主内容区必须使用 2 列 × 2 行的 CSS Grid，将四个象限均分为等面积 cell，并具备清晰分隔。
- **FR-005**: 四个象限的固定语义与顺序必须为：Q1 重要且紧急、Q2 重要不紧急、Q3 不重要但紧急、Q4 不重要不紧急；视觉排布按左上开始顺时针固定。
- **FR-006**: 每个象限块必须包含标题条、右上新建任务入口、按清单分组的内容区和空态。
- **FR-007**: 象限内任务必须按所属 `list` 分组展示，组头至少包含折叠/展开控件、清单图标、清单名称和任务数量。
- **FR-008**: 每条任务行必须至少展示 checkbox、标题、所属清单、日期或相对时间。
- **FR-009**: 点击 checkbox 时，完成态切换行为必须与全局任务模块一致。
- **FR-010**: 点击任务行正文时，必须打开与任务页一致的编辑弹窗。
- **FR-011**: 四象限页面的新建任务入口必须使用统一任务创建流程，并保证 `priority` 与 `dueDate` 默认值能使任务保存后落在当前象限。
- **FR-012**: 象限归属必须由 `priority + dueDate + today` 统一计算，不得以 `quadrant` 存储字段作为唯一真相。
- **FR-013**: 系统必须将优先级映射到重要度，并将时间映射到紧急度。
- **FR-014**: 紧急度阈值必须写死为：任务存在截止日期时，`D <= 7` 判定为高紧急，`D > 7` 判定为低紧急，其中 `D = dueCalendarDay - todayCalendarDay`。
- **FR-015**: 无截止日期任务必须按优先级直接映射：`P1->Q1`、`P2->Q2`、`P3->Q3`、`null->Q4`。
- **FR-016**: 高重要 / 低重要的判定必须来自优先级映射，且与四象限默认反演策略保持一致。
- **FR-017**: 系统必须满足明确验收语义：“今天 + 高优先级 -> Q1”、“约 1 个月后 + 低优先级 -> Q4”。
- **FR-018**: 当用户拖拽任务跨象限移动时，系统必须按唯一默认反演表同步更新底层 `priority` 与 `dueDate`。
- **FR-019**: 首版拖拽反演表必须完整覆盖四象限：`Q1 -> P1 + today`、`Q2 -> P2 + today+8d`、`Q3 -> P3 + today`、`Q4 -> null + today+8d`。
- **FR-020**: 当用户在同一象限内拖到另一个清单分组时，系统必须只更新 `listId`，不修改优先级和截止日期。
- **FR-021**: 页面必须支持整行拖动，不引入专门的拖动手柄列作为主交互。
- **FR-022**: 页面必须解决 checkbox 点击与拖拽冲突，保证 checkbox 可单独点击且不误触发拖拽。
- **FR-023**: 系统必须在跨日后对未完成任务重新计算 `D` 与象限归属，不依赖人工迁移。
- **FR-024**: 已完成任务的显示必须由页面右上角开关控制，并在各象限中以独立折叠区展示。
- **FR-025**: 首版必须移除旧 `important/urgent` 象限模型，不再将其作为查询、排序、渲染或回写依据。
- **FR-026**: 当前项目未投用，系统必须允许通过清空旧任务数据来配合本次模型重构。

### Non-Functional Requirements *(if applicable)*

- **NFR-001**: 重构后的四象限页面必须在桌面常见宽度下保持四宫格结构稳定、边界清晰、拖放目标明确。
- **NFR-002**: 页面交互必须优先复用现有任务模块的数据和编辑流程，避免再次分叉出第二套任务交互栈。
- **NFR-003**: 规则函数必须可单测，覆盖阈值、无截止日期、拖拽反演和跨日重算等关键边界。
- **NFR-004**: 本次需求不要求兼容旧四象限逻辑或保留旧数据。

### Key Entities *(if applicable)*

- **任务 Task**: 全局任务实体，至少包含 `completedAt/status`、`listId`、`priority`、`dueDate` 等字段；四象限只是它的派生视图。
- **任务清单 TaskList**: 任务的真实归属容器，用于四象限内分组显示与跨清单拖拽。
- **Quadrant Projection**: 由 `Task.priority`、`Task.dueDate` 与当前日期派生出的只读象限视图模型，不单独作为持久化真相。
- **Quadrant Defaults**: 针对 Q1~Q4 的唯一默认反演表，用于新建任务预填和跨象限拖拽回写。

## Out of Scope *(if applicable)*

明确不在本次功能范围内的内容：

- 四象限内任务的持久化排序能力
- 新增独立的 `quadrant` 数据库字段并长期缓存象限结果
- 移动端专门布局优化
- 顶部 `...` 菜单中除“显示已完成”外的其他功能
- 任务提醒、通知、自动化规则
